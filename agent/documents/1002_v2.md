# Submitting Finite Element Jobs to the Ansys HPC Cluster

## Scope

This document describes how engineers (and agents) submit Ansys Mechanical jobs to the GKN HPC cluster from the TRS analysis workflow. It covers why HPC submission is preferred over local solves, the Linux command-line interface, the MCP server available to agents, and the default presets for the supported analysis types.

> **Audience:** Written for human engineers. Agents working in this repository should read it as the source of truth for HPC submission parameters and tooling.

## Why Submit to the HPC

Local solves on engineering workstations are discouraged for production runs. The HPC nodes provide more cores and memory than the engineering workstations, reducing wall-clock time per load case (**throughput**); off-loading the solve also frees the local machine for pre/post-processing, model edits, and report writing while the run is in flight (**workstation availability**).

## Methods of Access

There are two supported entry points to the HPC. They are equivalent in effect; the choice depends on the operator.

### 1. Linux command line (`qansys` wrapper)

The CLI wrapper `qansys<version>` is the canonical interface. **It is only available on Linux engineering workstations** — Windows machines cannot reach the cluster directly and must either go through a Linux jump host or use the MCP server (Section 3.2).

### 2. MCP server (for agents)

Agents shall use the `mock-gkn-hpc` MCP server, which mirrors the `qansys` flag surface as MCP tools.

The server exposes a `submit_ansys_run` tool among others. See the [`mock-gkn-hpc` README](https://github.com/alex-pradas/mock-gkn-hpc) for the full tool surface.

## CLI Reference

`qansys<version>` accepts the following flags. They are the same fields exposed by the MCP `submit_ansys_run` tool.

| CLI flag        | MCP parameter | Required | Description                                        |
|-----------------|---------------|----------|----------------------------------------------------|
| `-i <file>`     | `input_file`  | yes      | Path to the `.ans` / `.cdb` input file             |
| `-o <file>`     | `output_file` | no       | Output file path (defaults to auto-named)          |
| `-j <name>`     | `job_name`    | no       | Descriptive job name (defaults to input stem)      |
| `-np <int>`     | `np`          | no       | Number of cores                                    |
| `-p <prod>`     | `product`     | no       | License product: `ansys`, `meba`, `mechs`          |
| `-a <MMDDhhmm>` | `start_time`  | no       | Scheduled start time                               |
| `--highprio`    | `high_prio`   | no       | Request high-priority queue                        |

The version is encoded in the binary name itself (`qansys2024r1`, `qansys2025r1`, ...). The TRS workflow is currently locked to `2024r1` — see Section 4.

## Default Presets

The settings below are the approved defaults for the TRS analysis. Deviations require sign-off from the lead stress engineer.

### Static Strength Analysis

```bash
qansys2024r1 -i runscript.ans -o runscript.out -np 8 -p meba
```

| Parameter       | Value           | Rationale                                                                  |
|-----------------|-----------------|----------------------------------------------------------------------------|
| Solver version  | `2024r1`        | Matches the locked Ansys version for the current TRS load loop             |
| Input file      | `runscript.ans` | Loads the model and the `limit_load_{i}.inp` cases (see *Loads Processing Design Practice* (1001)) |
| Output file     | `runscript.out` | Solver text output for archival                                            |
| Cores (`-np`)   | `8`             | Sized for the TRS mesh; sweet spot of solve time vs. queue contention      |
| Product (`-p`)  | `meba`          | Mechanical Enterprise Batch Academic license pool, used for strength runs  |

agents shall not submit using the script. Use the mock-gkn-mcp tool instead.

### Linear Analysis (small models, sanity checks)

For small linear-elastic checks — e.g. unit-load runs, sub-model verification, or a single load case used to validate the model build — the strength preset is over-provisioned. Use:

```bash
qansys2024r1 -i runscript.ans -o runscript.out -np 4 -p ansys
```

| Parameter      | Value     | Rationale                                                                    |
|----------------|-----------|------------------------------------------------------------------------------|
| Cores (`-np`)  | `4`       | Linear single-step solves do not benefit from `np=8` on the TRS mesh size    |
| Product (`-p`) | `ansys`   | Standard Mechanical pool; lower queue contention than `meba` for short runs  |

### Thermal-Only Analysis

For standalone thermal conduction runs that produce the temperature field consumed by the strength `runscript.ans` (`/input,thermal,inp,...`):

```bash
qansys2024r1 -i thermal_run.ans -o thermal_run.out -np 4 -p ansys
```

| Parameter      | Value     | Rationale                                                              |
|----------------|-----------|------------------------------------------------------------------------|
| Cores (`-np`)  | `4`       | Thermal solves are cheaper than the structural problem                 |
| Product (`-p`) | `ansys`   | Thermal does not require the batch-strength license pool               |

> The thermal output file shall match the `file_thermal` / `path_thermal` parameters expected by the strength `runscript.ans` (see Section 6).

## Failure Modes and Triage

Agents and engineers shall scan the run log (`ansys://{job_id}/log` over MCP, or the `.out` file from the CLI) for the markers below before declaring a run successful. Banner-only completion is **not** sufficient evidence that the solve converged.

| Symptom in log                                                | Likely cause                            | Action                                                                                              |
|---------------------------------------------------------------|-----------------------------------------|-----------------------------------------------------------------------------------------------------|
| `License ... not available` / queued for license              | Wrong `-p` or peak-hour contention      | Confirm `-p meba` for strength runs (Section 4.1). If correct, retry off-peak or escalate.          |
| `*** ERROR *** Element ... has zero or negative volume`       | Mesh corruption or bad CDB import       | Halt. Re-export the model; do not re-submit blindly.                                                |
| `*** ERROR *** ... pivot ratio ...` / `negative pivot`        | Under-constrained model, missing BC     | Halt. Verify `bc_fix` component and pilot/RBE3 connectivity against *Loads Processing Design Practice* (1001). |
| `*** ERROR *** Convergence not achieved` (nonlinear)          | Solver divergence                       | Halt. Do not adjust convergence tolerances without lead-engineer sign-off.                          |
| `max residual = ...` greater than `1e-6` on Sparse Direct     | Ill-conditioned matrix                  | Flag for review; results may still be usable but require sign-off.                                  |
| Run completes but `results.rst` is missing / 404 on MCP       | Solve aborted before postprocessing     | Treat as failed run. Inspect log for the actual error above the abort.                              |

The default response to any of the above is **halt and report**, not silent re-submission. Re-submitting a failed run without diagnosis has, in past load loops, masked model defects until late in the analysis cycle.

## Run Script Structure (`runscript.ans`)

For limit-load strength analyses, the top-level driver script (`runscript.ans`) shall contain the sections below, in this order. This is a **structural guideline**, not a code template — concrete parameters, paths, and component names depend on the specific TRS build. The reference implementation lives at `agent/previous_run/runscript.ans` and may be inspected for syntax.

1. **Batch-mode header and clean state.** Enter batch mode and clear any pre-existing model state from the solver session.
2. **String-parameter declarations.** Declare path/filename string arrays for the model, load files, thermal field, and each material card.
3. **User inputs block.** Reference temperature, uniform initial temperature, number of load cases (`n_lc`), and the absolute paths and filename stems for the model, loads, thermal input, and material files. This is the only block engineers should normally edit between runs.
4. **Reusable macros.** Define helper macros for repeated operations — at minimum `create_connection` (component-to-component coupling via `CEINTF`) and `create_pilot` (pilot-to-slave RBE3 for interface load application).
5. **Parameter save.** Persist the input parameters to a `.par` file so the run is self-documenting.
6. **Preprocessor — model import.** Enter `/prep7`, import the CDB model, and reset material assignments.
7. **Initial state.** Select all entities, clear load steps, set reference and uniform temperatures, set time = 1.
8. **Material assignment.** For each body component, select it, modify element material IDs, and `/input` the corresponding material card. The component-to-material-ID mapping shall be explicit in the script.
9. **Connections.** Build flange or contact connections between body components using the `create_connection` macro.
10. **Interface kinematics (pilot nodes).** Build the RBE3 pilot-node-to-load-area couplings for every interface listed in *Loads Processing Design Practice* (1001) (lugs, LPT, nozzle, plug, etc.). The pilot component names here **must** match the `pilot_*` names produced by `ductile-loads`.
11. **Boundary conditions.** Apply fixity at the bearing component (`bc_fix`) consistent with the *Loads Processing Design Practice* (1001) statement that the bearing reacts as a BC, not as a loaded interface.
12. **Solution setup.** Enter `/solu` and set the analysis type (`antype,static` for the strength preset).
13. **Thermal field application.** `/input` the thermal results file produced by the thermal-only run (Section 4.3).
14. **Load case loop.** A `*do` loop over `1..n_lc` that, per iteration: clears any prior force loads, `/input`s the corresponding `Limit_{i}.inp` (or `limit_load_{i}.inp`) file, and calls `solve`.
15. **Cleanup.** Remove intermediate solver files (`.emat`, `.esav`, `.osav`, `.full`, `.rdb`, `.ldhi`) to keep the run directory archive-sized.
16. **Finalize and exit.** `finish` and `/exit,nosav`.

> **Consistency check.** The pilot-node component names in step 10 (`pilot_lug_port`, `pilot_lpt`, ...) and the load file naming convention in step 14 are the contract between this script and `ductile-loads`. Any deviation from *Loads Processing Design Practice* (1001) will silently break the load application.

## Queue Etiquette

The HPC is shared across teams. Apply the following:

- **Right-size `-np`.** The TRS strength preset is benchmarked at `np=8`; do not request more cores expecting a linear speedup — the solver scales sub-linearly past that point on this mesh, and the extra cores cost queue throughput for everyone else. For linear or thermal-only runs, drop to `np=4`.
- **`--highprio` is reserved.** High priority shall only be used for time-critical runs that block a customer deliverable, with lead-engineer awareness. Routine load-loop submissions go through the normal queue.
- **Avoid mass simultaneous submissions.** When clearing a full envelope of limit loads, the load-case loop inside `runscript.ans` (step 14 above) is preferred over submitting one HPC job per load case — it consumes one license slot, not N.
- **Clean up artifacts.** Use `delete_results` (MCP) or the equivalent CLI cleanup to free the runs directory once outputs are archived. Stale jobs slow `list_jobs` and consume disk.

## Workflow

The complete submission chain is:

1. Generate the limit-load `.inp` files per ***Loads Processing Design Practice*** **(1001)** using `ductile-loads`.
2. Stage `runscript.ans` in the working directory alongside the `limit_loads/` folder.
3. Submit the run using the preset in Section 4 (CLI on Linux, or MCP for agents).
4. Poll for completion. From the CLI this is the queue manager; from MCP, read `ansys://{job_id}/log` until the solver banner reports completion, then fetch `ansys://{job_id}/results`.
5. Archive the log, results, and `meta.json` alongside the run inputs.

## Tools Available

- **`qansys2024r1`** — the CLI wrapper on the Linux engineering workstations.
- **`mock-gkn-hpc`** — MCP server, hosted on PyPI, delivered via `uvx`. Same parameter surface as the CLI.
- **`ductile-loads`** — produces the `.inp` files consumed by `runscript.ans`. See ***Loads Processing Design Practice*** **(1001)**.

## Lessons Learned

1. Running locally on a workstation has, in past load loops, blocked the engineer for a full afternoon per envelope. HPC submission is the default for this reason.
2. Using the wrong license product (`-p ansys` instead of `-p meba`) has resulted in license-queue waits during peak hours. The strength preset (`-p meba`) maps to the pool sized for batch strength work.
3. Mismatched solver versions between local and HPC runs have produced non-trivial result deltas. Always pin the version (currently `2024r1`) for the duration of a load loop.
